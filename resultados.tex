\section{Diagrama de Caso de Uso}

O diagrama de caso de uso detalha as interações entre os atores e o sistema. Foram identificados três atores distintos, cada um representando um perfil de acesso diferente dentro da plataforma: \textit{Viewer}, \textit{Editor} e \textit{Owner}. A especificação completa de cada caso de uso encontra-se no Anexo A.

\section{Arquitetura do Protótipo}

O protótipo foi construído segundo a arquitetura cliente-servidor, composta por dois módulos independentes: o \textit{back-end}, implementado com Spring Boot, e o \textit{front-end}, desenvolvido com Angular. A Figura~\ref{fig:arquitetura} apresenta uma visão geral dos componentes do sistema e dos canais de comunicação entre eles.

\begin{figure}[H]
    \centering
    \includegraphics[width=15cm]{figuras/desenho-da-arquitetura.jpeg}
    \caption{Arquitetura do protótipo}
    \begin{center}
        {\small Fonte: Elaborado pelo autor}
    \end{center}
    \label{fig:arquitetura}
\end{figure}

A comunicação entre os módulos ocorre por dois canais distintos: requisições REST via HTTP para as operações de persistência e autenticação, e uma conexão persistente via WebSocket para a sincronização colaborativa em tempo real.

O \textit{back-end} foi organizado em camadas seguindo o padrão MVC, compreendendo controladores REST, serviços de negócio, repositórios JPA para o PostgreSQL e repositórios MongoDB para os documentos de diagrama. A segurança é gerenciada pelo Spring Security com tokens JWT armazenados em \textit{cookies} HttpOnly, protegendo todos os \textit{endpoints} da API. O servidor WebSocket opera com um \textit{broker} STOMP no endereço \texttt{/ws}, com prefixo de aplicação \texttt{/app} para as mensagens enviadas pelo cliente e prefixo de tópico \texttt{/topic} para as transmissões do servidor.

O \textit{front-end} é estruturado como uma \textit{Single-Page Application} (SPA), com responsabilidades distribuídas entre componentes Angular, serviços e \textit{interceptors}. O componente central de diagrama integra a biblioteca GoJS para a renderização e manipulação interativa do canvas. O \texttt{CollaborationService} encapsula toda a comunicação WebSocket, enquanto o \texttt{DdlService} gerencia as operações de importação e exportação DDL.

\section{Funcionalidades Implementadas}

As subseções a seguir descrevem as funcionalidades que compõem o protótipo desenvolvido.

\subsection{Autenticação e Autorização}

O protótipo implementa um fluxo de autenticação, com a realização de \textit{login} com credenciais. Após a autenticação bem-sucedida, o servidor emite dois tokens JWT: um \textit{access token} de curta duração e um \textit{refresh token}, ambos armazenados como \textit{cookies} no navegador do cliente. As rotas da aplicação são protegidas por \textit{guards} no \textit{front-end} e por um filtro JWT no \textit{back-end}, que intercepta e valida o token em cada requisição. Quando o \textit{access token} expira, o \textit{interceptor} do Angular aciona automaticamente o \textit{endpoint} de renovação, obtendo um novo par de tokens de forma transparente ao usuário.

\subsection{Gerenciamento de Projetos e Times}

O sistema permite ao usuário criar e gerenciar projetos de modelagem. Cada projeto possui um time de colaboradores, para o qual o criador pode convidar outros usuários cadastrados na plataforma. A gestão de projetos e times é realizada por meio de uma interface de \textit{dashboard}, com operações de criação, leitura, atualização e exclusão comunicadas ao servidor e persistidas no banco de dados.

\subsection{Editor de Diagramas ER}

O editor de diagramas constitui o componente central do protótipo. Construído com a biblioteca GoJS, o canvas oferece as seguintes capacidades de modelagem:

\begin{itemize}
    \item Adição e remoção de entidades (tabelas);
    \item Adição, edição e remoção de atributos, com configuração de tipo de dado, chave primária, chave estrangeira, unicidade, restrição \textit{NOT NULL}, auto-incremento e valor padrão;
    \item Criação e exclusão de relacionamentos entre entidades, com definição da cardinalidade;
    \item Reposicionamento livre dos elementos na área de desenho.
\end{itemize}

O estado completo do diagrama (entidades, atributos, relacionamentos e posicionamentos) é serializado no formato JSON e persistido no MongoDB ao final de cada sequência de ações.

\subsection{Colaboração em Tempo Real}

A funcionalidade de colaboração permite que múltiplos usuários de um mesmo time trabalhem simultaneamente no mesmo diagrama. Ao abrir um projeto, o cliente estabelece uma conexão STOMP sobre SockJS com o servidor e se inscreve no tópico \texttt{/topic/diagram/\{projectId\}}. Quando um usuário seleciona uma entidade para edição, um evento de \textit{lock} é enviado ao servidor via \texttt{/app/diagram/lock} e imediatamente propagado a todos os demais clientes conectados. Enquanto o \textit{lock} está ativo, a entidade correspondente fica bloqueada para edição pelos outros colaboradores, prevenindo conflitos de concorrência. O \textit{lock} é liberado automaticamente por um mecanismo de \textit{timeout} no servidor caso o usuário não o libere explicitamente.

\subsection{Importação e Exportação DDL}

O protótipo suporta a interoperabilidade com outros ambientes por meio de operações DDL no dialeto MySQL. A exportação converte o modelo do diagrama em instruções SQL (\textit{CREATE TABLE}) e a importação analisa um \textit{script} SQL fornecido pelo usuário para reconstruir o diagrama correspondente no \textit{canvas}. Ambas as operações são intermediadas pelo \textit{endpoint} \texttt{/api/ddl} no \textit{back-end}.
